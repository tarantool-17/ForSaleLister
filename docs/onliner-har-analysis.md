# Анализ сценария размещения на Onliner

Источник наблюдений: локальный HAR `baraholka.onliner.by.place.har`, записанный при размещении
объявления. Сам HAR не добавлен в репозиторий: он содержит персональные данные страницы аккаунта и
может содержать действующие данные сессии.

## Авторизация

В HAR нет самого входа: запись начинается уже в авторизованной сессии. Страница Барахолки получает
пользователя из общей сессии Onliner. Старый JavaScript страницы также показывает внутренний обмен
cookie `onl_session` на краткоживущий access token для API загрузки изображений.

Этот обмен не следует воспроизводить в отдельном HTTP-клиенте: это внутренний, недокументированный
контракт, а извлечение или импорт cookie создаёт ненужный риск. MCP-инструмент использует отдельный
постоянный профиль Chrome/Edge/Chromium. Пользователь сам выполняет вход, MFA и CAPTCHA в видимом
окне; пароль, cookie и коды никогда не передаются инструменту.

## Выбор категории

Категории Барахолки представлены форумами:

```text
GET https://baraholka.onliner.by/
  -> ссылка viewforum.php?f=<forum_id>
```

В наблюдённом сценарии кофемашина была размещена в категории `Мелкая кухонная техника`,
`forum_id=1682`. На финальной отправке этот идентификатор был передан полем `f=1682`.
Поле `topic_bar_cat=1` обозначало тип `Продам`.

Идентификаторы категорий нельзя считать постоянными. `onliner_find_categories` каждый раз читает
живую главную страницу, ранжирует варианты, а `onliner_preview_listing` отдельно проверяет, что
выбранный `forum_id` всё ещё имеет ожидаемое название. Неоднозначный результат должен быть разрешён
человеком или агентом до preview.

Значение `region` также является внутренним ID. `onliner_find_regions` читает его вместе с видимым
названием из актуальной формы выбранной категории; preview проверяет оба значения.

## Загрузка фотографий

Наблюдённый браузерный поток:

1. `POST https://upload.api.onliner.by/upload` как `multipart/form-data` с файлом и метаданными типа
   `fleamarket-photo`.
2. Ответ `202 Accepted` содержит ID/URL операции и статус `uploaded`.
3. Браузер опрашивает `GET /upload/<id>` до статуса `processed`.
4. Ответ содержит URL вариантов `48x48`, `80x80`, `100x100`, `800x800`.
5. Страница добавляет в `message` BBCode вида `[img=<filename>]<800x800 URL>[/img]` и выбирает первое
   успешно обработанное изображение как `topic_icon`.

Инструмент не копирует внутренний token flow. Он задаёт файлы живому `input[type=file]` и ждёт, пока
JavaScript Onliner обработает каждое изображение и вставит соответствующий BBCode. Лимиты из формы:
JPG/JPEG/PNG/GIF, не более 10 МБ на файл.

## Отправка объявления

Финальный запрос из HAR:

```text
POST https://baraholka.onliner.by/posting.php?mode=post
Content-Type: application/x-www-form-urlencoded
```

Значимые поля:

- `creation_time`, `form_token` — одноразовые значения актуальной формы;
- `mode=post`, `post=1`;
- `f` — `forum_id` категории;
- `topic_bar_cat=1` — `Продам`;
- `subject`, `topic_desc`, `message`;
- `region`;
- `topic_currency`, `topic_price`, `topic_torg`;
- `topic_icon`, `file`.

Успешный ответ — `302` на `viewtopic.php?f=<forum_id>&t=<topic_id>`. Инструмент открывает живую
форму перед каждой попыткой, поэтому CSRF-поля получает Onliner, а не HAR.

## Защитные свойства инструмента

- Preview не загружает фото и не изменяет аккаунт; он фиксирует точный пакет на 24 часа.
- Publish требует тот же `approval_id` и точную строку `PUBLISH APPROVED LISTING` после явного
  пользовательского одобрения показанного пакета.
- Межпроцессный claim создаётся до загрузки и клика. Для одного `approval_id` возможна только одна
  попытка публикации.
- Запись попытки создаётся до финального submit. Таймаут даёт `результат неизвестен`; повтор запрещён.
- При возможности результат сверяется по redirect или по новой теме в выбранной категории.
- CAPTCHA, MFA, проверка телефона/личности, обязательная оплата и юридические подтверждения
  передаются пользователю, а не обходятся автоматически.
- Возможный дубликат того же аккаунта блокирует выдачу `approval_id`.

Это автоматизация живой веб-формы, а не официальный публичный API Onliner. Изменение DOM или
серверных правил должно приводить к безопасной остановке и обновлению селекторов, а не к попытке
угадывать новый контракт.
